# Implement

## Goal

Make the change the issue asks for, prove it with tests and the repo's checks, and deliver it as a PR ready for review. When a spec exists it made every decision: build what it says, and treat a gap or a contradiction as a deviation, not a redesign. You also revise the PR (`review_findings`, `answered`, `ci_failed`, `conflict`, or a person's `prompted` instruction).

## Done looks like

**Asking first, on `track: express`.** With no spec, a `delegated` or `design_approved` run asks before any code what a spec would have asked: product calls and the technical approach, in `questions` with `needs_input` (`linear-reporting`), each with your suggestion first, then stops. Ask only what the issue, triage's brief and the approved boards leave open; when they decide everything, build. The calls under `## Decided at Design Review` in `specs/<ISSUE-ID>/design/notes.md` were confirmed with the design: they're settled, so never ask them again. Don't ask about infrastructure or CI (tooling, workflows, deploys, how a dependency is set up): take your suggestion, and say in the session what you chose and why, so a reply can change it as a follow-up. With `trigger: answered`, the answers are the plan; record them in the PR's Decisions as `(asked during the build)`.

**Delivering:**

- You've read the issue, its briefs, `specs/<ISSUE-ID>.md` when it exists (for a part of a split issue, the parent's spec and only this part) and every file under its Required reading.
- When `specs/<ISSUE-ID>/design/` exists, the screens match its approved boards, with exact values copied from the board markup and the suggestions in `notes.md` applied.
- With `trigger: spec_approved` or `design_approved`, the `prompt`'s suggestions amend the spec: your first commit updates `specs/<ISSUE-ID>.md` to match and records them in Decisions as `Asked: approval → approved with: <suggestions>`.
- What the spec cites still holds on `main` (`git log origin/main --since=<spec date> -- <paths>`). Drift that changes a behaviour or a decision is a question; smaller drift you adapt to and note.
- Every acceptance criterion (or the spec's Validation criteria) is met and tested. With no spec, it's the smallest correct change at the root cause.
- A bug fix comes with a test that failed on the unchanged code for the bug's reason, in the same commit as the fix.
- When `AGENTS.md` names a seed for tests and your change adds a model, field or state the seed can't make, the seed is extended in this PR.
- The repo's checks from `AGENTS.md` pass: lint, types, the tests for what you touched, and the build. Never claim a check you didn't run.
- The diff meets `ground-rules` and holds nothing out of scope: no debug code, scratch scripts or logs.
- When the PR changes what shows on screen and `EVIDENCE_DIR` is set, `EVIDENCE_DIR` holds one visual's recordings and its `visual.json` (below), and the PR shows it per `git-text`. With no `EVIDENCE_DIR`, the PR says there's no visual.
- The PR is on the spec's branch (with `origin/main` merged in when it's behind) or a new one per `git-text`, written per `git-text` (replacing the spec PR's placeholder), marked ready, labelled `factory` if you opened it, and linked on the session. Report without waiting for its checks: the console hears when CI fails.

**Revising**, on the same branch and PR. The brief's `prompt` holds the findings (unambiguous ones aren't on GitHub, so it's their only source), the person's answers, the failed run or the base branch:

- Each review finding is fixed or declined with a reason, answered in one PR comment once pushed, in the brief's order:

  ```markdown
  **Round 1 findings**

  1. Fixed in `abc1234`: what changed, in a line.
  2. Not changed: why, in a line.
  ```

- With `trigger: answered`, each decision is carried out (or the PR left as it is where it says so) and answered in one PR comment, in order.
- A review comment a person left on the PR has a one-line reply in its thread, and is resolved only when you made the change.
- A failed check has its cause fixed, not its symptom, and one PR comment naming the job, the cause and the fixing commit.
- A conflict is cleared by merging `origin/<base>` in, keeping both sides' behaviour, with the full checks run. A conflicted lockfile is regenerated by its package manager, and the merge is the only commit, so the console can see nothing reviewed changed. One PR comment lists each conflicted file and how it was resolved. When both sides can't hold, it's a question and nothing is pushed.
- For a finding with a guard, or a bug you fixed, the cheapest guard against its whole class (a type or lint rule, then a test, then a rule in `AGENTS.md` or a lesson) is in this PR when it uses the repo's tooling, stays small and changes nothing outside the issue. Otherwise it goes in the report's `guards`. Never both; say which in the PR.
- A revision that changes what shows on screen records the visual again, and the PR points at the new one.
- The description is updated wherever it became false.

**The visual** is recorded with the repo's Playwright setup at 375 × 812, from local data and the seed, never production. The evidence job builds it after you finish and uploads it; never commit the recordings.

- **Screens**, for new or changed screens: a PNG of each, at most four in all, the ones that matter most first. A changed screen also gets its before, from `origin/main` (before your first change, or a worktree of it). A caption is at most 22 characters of letters, digits, spaces and `, . : ' ( ) & / + -`. `visual.json`: `{ "title": "What changed: the Ingredients section and the saved recipe", "screens": [{ "caption": "Ingredients", "before": "1-before.png", "after": "1-after.png" }, { "caption": "The saved recipe", "after": "2-after.png" }] }`.
- **A video** instead, when the change is an interaction or a flow: one walk through it, under 30 s, paced for a person to follow, copied to `walkthrough.webm`. Use `test.use({ viewport: { width: 375, height: 812 }, launchOptions: { slowMo: 150 }, video: { mode: 'on', size: { width: 375, height: 812 } } })`, hold each state 1.5 s and type with `pressSequentially(value, { delay: 60 })`. `visual.json`: `{ "title": "Walkthrough: adding an ingredient that isn't on the list", "video": "walkthrough.webm" }`.
- File names are lower-case words, digits and hyphens. Captions are at most 22 letters, digits, spaces and plain punctuation. The title names what's shown, under 150 characters.

## What you may touch

The repo, on the work's branch. Never push to `main`, and never amend, rebase or force-push a pushed commit. Make mechanical deviations (a moved import, a renamed symbol, a file a step obviously needs, a sketch adapted to real types) and list them in the PR. A design deviation (a changed behaviour, public signature, copy or file list) is a question, never a change.

## Report

Per `factory-run`:

- `done` with `next: review`.
- `needs_input` with `questions` (format in `linear-reporting`), your suggestion first, for express's questions before coding, a design deviation or drift.
- `blocked` when a criterion can't be met as specced or something outside the factory must change.
- `failed` after three failed attempts at the same check, with an `error` saying what you tried.

Add `guards` and `workarounds` when you have them. Propose a lesson in the PR when a deviation was something the spec should have caught.
